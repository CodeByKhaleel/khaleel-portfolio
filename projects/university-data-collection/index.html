STEP 01 · SOURCEUniversity course and intake details live across pages with different structures.

Illustrative pipeline · no live CRM records
Source-specific collection

I matched each script to its university’s page structure, navigation, and content formats, then organized the collected records for review.

One script per university

University pages presented course and intake information in different structures, so the scripts followed each source’s own layout and navigation.

The scripts gathered course names, intakes, attendance details, duration, and other information used to keep the internal CRM current. The output went through a quality-control step before import.

Match each source page

The work involved browser navigation, page-specific selectors, pagination, dropdowns, dynamic pages, and data normalization. Different site behavior meant each script needed to match its own source.

My contribution

Script creation and maintenance

I created and maintained source-specific extraction scripts, then integrated them with shared normalization functions for intake dates, course level, campus, duration, and attendance type.

Technical context

TypeScript + Playwright

The scripts used TypeScript and Playwright with shared processing and storage components from the wider project.

Why the process mattered

Useful data needed a quality gate.

Preparing generated files for QC kept extraction separate from the final CRM update, so data could be checked before it reached operational records.
