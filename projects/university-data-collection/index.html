What changed from site to site

Pagination, dropdowns, clicks, content formats, and bot defenses made a single generic extraction path unreliable.

One script per university

Each university could expose the needed course information differently. I created 37 university scripts and contributed edits or updates across 72 universities.

The scripts gathered course names, intakes, attendance details, duration, and other information used to keep the internal CRM current. The output went through a quality-control step before import.

Handle the page that exists

The work involved browser navigation, page-specific selectors, pagination, dropdowns, dynamic pages, and data normalization. Different site behavior meant each script needed to match its own source.

A real limitation: Cloudflare protection was difficult and was not solved in this project. The case study should not imply that it was bypassed.

My contribution

Script creation and maintenance

I created 37 university scripts and updated or edited scripts across 72 universities. I also integrated the scripts with shared normalization functions for fields such as intake dates, course level, campus, duration, and attendance type.

Technical context

TypeScript + Playwright

The scripts used TypeScript and Playwright. The wider project included shared processing and storage components; integrating shared functions does not mean I authored those components.

Why the process mattered

Useful data needed a quality gate.

Preparing generated files for QC kept extraction separate from the final CRM update, so data could be checked before it reached operational records.
