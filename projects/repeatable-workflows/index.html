Turning Repetitive Submissions into Repeatable Workflows

A configurable approach to the same problem repeated across portals: prepare the data once, describe each workflow, and make room for a person when the page needs one.

The problem

Every portal had its own rules.

Fields, page flows, uploads, verification, and conditional questions changed from one site to another. A separate bot for every portal would multiply maintenance.

Each submission meant someone re-entering CRM details into another external portal. The same information needed different formats, and the page itself could change depending on earlier answers.

The core design question was how to support new portal workflows without adding another portal-specific code path every time.

Describe the portal. Reuse the workflow.

I designed the JSON configuration model and workflow editor so each portal’s steps and conditions could live in configuration. The shared workflow could interpret that description, while config changes could be made without redeploying the code.

Design choices

What I built, and why.

Prepare data before the run

A Python preparation step reshapes CRM names, dates, country codes, phone numbers, and yes/no values into portal-ready values. Missing fields are surfaced before the browser starts.

Let the page determine the branch

Configuration rules check what is actually present on the page, follow relevant answers, and skip questions that do not apply. This lets one workflow cover multiple form paths.

Design for human checkpoints

My manager proposed human involvement for verification steps. I implemented the handoff so a person can complete an OTP or CAPTCHA and the workflow can continue afterward.

Make failures actionable

Retries handle small transient failures such as slow pages. Failure labels distinguish configuration, portal changes, connection issues, and runs needing a person.

The outcome

A workflow that could grow through configuration.

More portal variation could be handled while keeping the shared codebase consistent. The project continues to run internally, so its metric snapshot changes over time.
